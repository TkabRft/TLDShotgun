# Ammunition source authoring

code-synced: 2026-11-08

The editable [Ammunition.blend](Ammunition.blend) contains one isolated asset scene, eleven named asset collections, twelve mesh objects, ten packed textures, and an icon-lighting setup. It includes three projectile portions and four shell/box pairs: red buckshot, dark blue slug, green birdshot, and grey scrapshot. Manufactured boxes retain their original artwork; scrapshot retains its unprinted improvised carton, now grey. The carton is open at one end with a bent-back flap and **six actual shell meshes** visible inside. No new lettering or floating text is added.

Shell variants retain the original shell geometry, UVs, brass bases, and proportions. The carton uses the original box dimensions as its baseline, with thin folded panels, creases, rough edges, and six copies of the unchanged shell geometry. Small dimensional differences come from cardboard thickness and dents. The original FBX/textures and existing asset GUIDs remain unchanged; load-specific exports and materials supply the colored variants. The displayed pile counts are decorative and independent of material quantities and combat pellet settings.

See [the box preview](previews/ShotgunScrapshotBox.png) and the other previews in `previews/`. FBX files are Unity source inputs under `Assets/Shotgun/Imports/`; corresponding GLBs in `exports/` are self-contained inputs for the Unity-free builder. The eleven inventory PNGs are transparent 256 x 256 renders. The separate Scrapshot HUD is a flat white/alpha 183 x 436 silhouette with cut-metal shapes, matching the existing ammunition HUD. Its PNG is 184 x 436, with a transparent column on the right for BC3 block alignment; its Sprite rect excludes that padding. Explicit opaque Standard materials under `Assets/Shotgun/Materials/` reference ten base-colour textures. Both build paths assign materials by exact slot name, including the carton and shell slots.

## Live authoring phases

Use the workspace Blender MCP instructions. `author_ammunition.py` is now a safe loader, not an automatic background scene rebuild. Importing the builder changes nothing. Load `source/ammunition_assets.py` into a namespace and keep that namespace in `bpy.app.driver_namespace`. The functions select only `TLDShotgun_Ammo_Workshop`; unrelated scenes are preserved.

For a fresh task scene, deliberately call `texture_phase()`, `pile_phase()`, and `shell_box_phase()` in order, inspecting the results between phases. Existing populated collections reject accidental rebuilding. To resume a saved project, load the module and attach to the named scene/collections; do not rerun geometry constructors. The source builder intentionally contains no added lettering pipeline.

For a fresh scene, load `source/ammunition_colors.py` and call `author()` after those base phases, then `grey_carton()`. The color phase rejects existing variant collections. To resume the saved file, attach without calling `author()`. `recolor()` preserves wear and neutral/brass pixels using the original atlas hue; the factory box masks differ by load. `render(kind)` refreshes both previews/icons for that load. The exported pickup/inventory variants do not change first-person weapon animation meshes.

Call `render_asset(name)` for a 512 px preview and `render_asset(name, 256, True)` for its inventory icon. `export_phase()` exports explicit mesh selections with metre units to FBX and GLB. `roundtrip_phase()` imports each format into temporary scenes and checks fresh objects, dimensions, triangle counts, UVs, and texture loading. Temporary imports are removed without touching the source scene.

Factory box renders use the opposite camera azimuth to the open scrapshot carton so their printed fronts face the viewer and the top label reads toward the camera. Keep scrapshot's existing framing when changing factory icon views. This is render framing only; pickup model transforms and inspection settings are unchanged.

`prepare_crafting_presentation.py` derives twelve separate crafting textures from the existing HUD/inventory PNGs, without Blender or model edits. Four monochrome shell silhouettes and the empty casing reuse the weapon UI artwork; three projectile-material silhouettes use the existing inventory artwork; four colored shell previews angle the existing inventory images 40 degrees clockwise. Outputs and stable metadata live under `Assets/Shotgun/Icons/Crafting/`. The script adds their source Addressables entries, manifest registrations, and four shell-name localization keys while preserving inventory/HUD inputs and existing translations. White RGB in transparent silhouette pixels prevents dark BC3 fringes. Use `--check` to verify deterministic output without writing, and optional `--preview <path>` to inspect a contact sheet. The ordinary ammunition validator runs the source checks; the mod's crafting presentation harness also checks cooked textures and UI/quality helpers.

The Blender renderer does not overwrite the HUD. Run `source/render_scrapshot_hud.py` with Pillow to regenerate its SVG and padded PNG from the existing buckshot outer silhouette and the editable cut-metal polygons. `source/ScrapshotHUD.svg` retains the 183 x 436 logical canvas; the game consumes `Assets/Shotgun/Icons/ico_DoubleBarrelScrapshotHUD.png` and the manifest's explicit `[0, 0, 183, 436]` Sprite rect. The black mask polygons become transparent cutouts, not opaque black paint. Preserve that PNG's metadata GUID. Do not stretch the art to the padded width: the original Sprite geometry, UV transform and display proportions are retained. The user confirmed the icon update in game; recheck the current texture for absence of the BC3-to-RGBA32 fallback warning.

`save_library(path)` stages only the task scene and its dependencies. In a separate Blender process, `source/verify_blend.py -- --normalize` converts that staged library into the normal standalone `Ammunition.blend`, reopens it, and verifies scene scope, finite geometry/UVs, closed meshes, packed-texture hashes, and six distinct shells inside the carton. Without `--normalize`, the verifier only reopens/checks the final file. Normalization is an intentional overwrite step, not a connection check.

`source/prepare_art_materials.py` writes the ten owned Unity materials and their texture metadata. `source/prepare_color_materials.py` also synchronizes the package material manifest, shell visual-wrapper variants and box material overrides. Existing gear prefab IDs/GUIDs and icon GUIDs are preserved; missing old icon metadata is recovered from Addressables. Neither script invokes Unity or builds a package.

## Validation and limits

`asset-geometry.json`, `asset-roundtrip.json`, and `asset-blend-validation.json` record the final checks. All source meshes have zero nonmanifold edges. Triangle counts are 3,960 / 8,500 / 440 for the three portions, 552 per single shell, 3,084 per manufactured box, and 6,784 for the open carton with six shells. All twenty-two FBX/GLB round trips passed; maximum dimension error was below 0.000001 m. Ten packed texture hashes match the source PNGs. The six-shell carton visual does not create extra inventory items or change its 240 g stack weight.

Run `python source/validate_art.py` to verify current file hashes, material/texture GUID references, PNG headers, and the recorded geometry/interchange reports. It checks inventory PNGs at 256 x 256 and the separate HUD texture at 184 x 436. The package tests separately validate the 183 x 436 Sprite rect and transparent padding. These checks do not establish Unity shader appearance or game acceptance.

`prepare_ammunition_data.py` regenerates the new material definitions, updated ammo packaging JSON, six optional recipe templates, localization additions, and `ammunition-definitions.json`. It also updates existing source-prefab weights and replaces the old Bullet references for buckshot/birdshot. Existing recipe names, prefab IDs, and translations are preserved. Edit the generator when changing recipe data, then regenerate and review the result.

Ammunition weights describe the whole default item: 0.040 kg for singles and 0.240 kg for six-round boxes. Native stack accounting divides by `UnitsPerItem`; source/package validation checks the resulting 0.040 kg per round. Prefab weight synchronization accepts any previous numeric value and is idempotent. Single/box names share each load's ammunition wording under existing localization keys; runtime quality formatting is described in [ammunition reference](../../docs/AMMUNITION.md#quality-labels-and-registration).

The generator adds 48 full-name condition variants: six quality labels for each of the eight shell localization keys. These are source/package inputs; runtime selection uses the native ammunition condition table. The validators check every variant and preserve Gunsmithing as both the applied and improved skill on default/optional shell recipes. Runtime output-condition settings do not change recipe ingredients or asset identifiers.

Run `python validate_ammunition.py` for non-compiling recipe/material/weight/artwork checks and boundary cases evaluated from the pure spawn expressions in the C# source. This does not replace compilation or in-game tests.

Use `python validate_ammunition.py --ammo-only` for focused ammunition checks. The legacy default also parses spawn expressions and currently does not match the revised spawn policy; use the existing spawn harness for that subsystem. The production maintenance harness additionally links `ShotgunAmmoHarvest.cs` and checks all four loads and both forms, repeated setup, unchanged gear yields, missing powder, and per-round amounts for one/three/six units. It does not execute native stack harvesting, which remains a game check.

## Unity-free package build

`no-unity-build.json` is the declarative build input. It pins the immutable checked-in `DoubleBarrel.modcomponent` by SHA-256 and selects compatible object/material/catalog templates. The workspace ModBuild pipeline consumes eleven GLBs, ten material textures, twelve inventory/HUD icons, twelve crafting textures and current ModComponent JSON directly. Its audio section embeds six existing PCM16 WAVs from `Assets/Shotgun/Sounds/` into the DLL, preserving their hashes and waveform. Runtime creates verified clips in memory rather than decoding the original FSB clips or extracting sound files; see [weapon animation and audio](../../docs/WEAPON-ANIMATION-AUDIO.md). No Unity Editor, Hub, editor module or container is used or downloaded. The earlier SDK editor utility is retained as source-authoring guidance; it is not part of this build path.

The generated package supplies eleven authored prefabs and 150 native Unity objects, including a separate HUD Sprite and twelve crafting texture/Sprite pairs. Six prefab/icon pairs replace the existing manufactured-ammunition container/catalog targets under their existing addresses; five prefabs are additions. All 244 original non-container objects remain byte-for-byte unchanged, including shaders' references, existing clips and sounds. New GameObjects have mesh renderers, filters and bounds-derived box colliders. Textures use BC1 for opaque materials and BC3 for transparent icons. Original GUIDs and game IDs are unchanged; deterministic 64-bit internal path IDs have collision checks.

The builder replaces entire owned data sections with the current material, recipe, harvest, localization, spawn and weight definitions, using lowercase filenames. It rejects case collisions, resolves all 18 gear definitions using ModComponent's lookup rules, and checks nine current default blueprints without legacy alternatives. It updates Addressables entries, preload dependencies, size, hash and nonzero CRC, then reopens the package and checks local/external references against both bundles. The runtime DLL embeds the generated package under the existing resource name. The checked-in template is left unchanged and is never silently substituted for a missing generated result.

Structural validation, real JSON-consumer lookup and an isolated .NET 6/Harmony lifecycle test pass. Earlier checks missed case-sensitive lookup and retained legacy data; the first generated package failed registration in game. The corrected runtime streams its package directly into ModComponent and leaves only the framework's standard working cache. Known old standalone archives are removed after successful registration. See [embedded asset loading](../../docs/ASSET-LOADING.md) for lifecycle and migration details.
